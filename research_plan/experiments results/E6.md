# E6 — Scalability

Time + peak GPU memory for every method on ogbn-arxiv (169K), MCAR @ 80%, 800 epochs,
locked config. Point: NESS runs at GNN-scale memory; the auxiliary objectives add
wall-clock but no memory blow-up.

**Source:** `experiments/e6_scalability.sh` →
`ogbn_benchmarks/results/e6_scalability_20260725_091754/`.

**Status:** DONE.

| Model | Time (s) | Peak GPU (GB) | Test F1 |
|---|---|---|---|

| MATE | 1569 | 1.26 | 0.445 |
| **NESS** | 2355 | **1.31** | 0.438 |

## Reading

- **Memory:** NESS peaks at 1.31 GB, essentially the same as MATE (1.26 GB) and far
  within a single-GPU budget. The SSL objectives + prefill + contrastive add no memory
  blow-up; NESS scales like a standard clustered GNN.
- **Time:** NESS is the slowest (2355 s), ~1.5x MATE and ~6x FP. This is the cost of the
  auxiliary objectives (structural target sampling, PPR view, contrastive) computed each
  epoch. Still minutes on a single GPU.

## Framing for the paper

Report as: NESS trains at GNN-scale memory (comparable to MATE), confirming the method
adds no scalability penalty in memory; the higher wall-clock reflects the auxiliary
objectives and remains practical on a single GPU. Do NOT claim equal training time —
frame honestly as a memory-parity result with a modest time overhead.
